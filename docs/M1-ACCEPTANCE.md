Concurrency tests выполняются на настоящем PostgreSQL с отдельными соединениями и барьерами синхронизации. SQLite и mocked repository не подтверждают поведение блокировок. API tests проверяют реальную авторизацию и rollback, UI tests — несколько критических цепочек, а не каждую декоративную деталь.

План по модулям: Auth — AUTH/RBAC, Users — invitation/membership/last-owner, Properties — scope/summary, Rooms/Beds — ROOM/BED/DATA/TX, Audit — AUDIT/TX. Unit tests покрывают чистые правила/валидацию, integration — ограничения и транзакции, API — контракт и доступ.

## Последовательность реализации после фиксации проекта

1. Выбрать runtime/framework, закрепить версии, создать каркас и CI.
2. Превратить DDL-проект в миграции, guarded procedures, роли БД; проверить с нуля.
3. Реализовать bootstrap, sessions, invites, RBAC и ограничения владельцев.
4. Реализовать inventory API с блокировками, versioning, idempotency и audit.
5. Создать минимальные mobile-friendly экраны настройки M1, выполнить UI checks.
6. Проверить backup/restore и безопасную конфигурацию развёртывания.
7. Выпустить отчёт M1 с реальными результатами тестов; только затем обсуждать M2.

Завершённым M1 считается работающая реализация этих сценариев с пройденными проверками и зафиксированными ограничениями. Текущая поставка завершает проектирование, не весь milestone разработки.
