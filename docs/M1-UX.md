# Мобильные сценарии M1

Проект интерфейса настройки foundation. Полное приложение владельца относится к M4. В M1 нужны только вход, настройка дома, комнаты/места и контроль изменений; это не финансовый dashboard.

## Навигация и визуальные правила

Основные пункты: **Дом · Комнаты · История**. «Сотрудники» в меню владельца. Управляющий видит комнаты, места и их операционную историю; управление доступом скрыто и защищено backend. Будущие разделы не показываются неработающими кнопками.

Ориентир ширины — 360–430 px, проверка с 320 px. Светлый фон, крупные числа, одно главное действие на экран, вертикальные карточки вместо широких таблиц. Основной текст 16 px; области нажатия не меньше 44×44 px. Статус обозначается текстом и иконкой, цвет только дополняет: свободно — зелёный, резерв — янтарный, ремонт — серый. Занято в будущем — синий.

Подписи доступны screen reader; фокус видим; контраст текста целевой 4.5:1. Ошибка рядом с полем, введённые данные сохраняются. В формах адаптировать клавиатуру к телефону/сумме. Суммы показываются «900 000 сум», в API отправляются точные decimal strings.

## Вход и первоначальная настройка

Вход: логин → пароль → «Войти». Ошибка «Не удалось войти. Проверьте логин и пароль», без раскрытия существования аккаунта. Во время отправки кнопка блокируется. Для приглашения — отдельная форма «Код приглашения, ФИО, пароль, телефон необязательно». После успешного принятия — переход ко входу.

После bootstrap владелец видит название дома и пустое состояние: «Комнат пока нет» → «Добавить комнату». Форма комнаты: номер, вместимость. После сохранения: «Комната 3 создана. Добавьте спальные места». Места не считаются свободными, пока не заведены.

## Дом

```text
┌────────────────────────────────┐
│ Ijara360                 Меню  │
│ Студенческий дом               │
│ Обновлено сегодня в 15:00      │
│                                │
│ Комнат          Мест настроено │
│   7  →              59  →     │
│                                │
│ Свободно    Резерв    На ремонте│
│  54 →       3 →        2 →    │
│                                │
│ [ Добавить комнату ]           │
│ Последние изменения           │
│ Место 3-1 добавлено · 14:56    │
│                                │
│ Дом       Комнаты      История │
└────────────────────────────────┘
```

Числа — иллюстрация состояния M1, не данные реального дома. Каждая карточка ведёт в список с тем же фильтром: «Свободно» → beds?status=AVAILABLE. «Мест настроено» → все неархивные места, «Комнат» → активные комнаты. После изменения данные перечитываются с сервера.

Карточки финансов, жильцов и камер пока отсутствуют. Экран не заявляет «54 свободно» о фактически заселённом доме до внесения проживания в M2; до начала M2 интерфейс имеет подпись «Настройка мест. Учёт проживания ещё не подключён».

## Комната и место

```text
┌────────────────────────────────┐
│ ‹ Комнаты          Комната 3   │
│ Настроено 7 из 9 мест          │
│ 5 свободно · 1 резерв · 1 ремонт│
│                                │
│ 3-1  Свободно       900 000 сум│
│ 3-2  Резерв         900 000 сум│
│ 3-3  На ремонте     900 000 сум│
│ …                              │
│ [ Добавить место ]             │
│ Изменить комнату · История     │
└────────────────────────────────┘
```

Добавление места: номер + месячная базовая цена → «Сохранить». Свободных слотов нет — кнопка недоступна с подписью «Все 9 мест настроены»; backend всё равно проверяет вместимость. При конфликте параллельной записи перечитать комнату, сохранить введённое и предложить другой номер/действие.

Карточка места: обозначение, статус, цена, причина резерва/ремонта, история изменений. OWNER видит «Изменить цену/номер» и действия архива; ADMIN — только изменение операционного состояния. «Занятие места» и данные жильца появятся в M2.

Перевод в резерв/ремонт: действие → короткая причина → подтверждение. Освобождение: «Вернуть в свободные» → причина → сохранить. В M1 нет автоматического снятия резерва и обещаний, что место закреплено за конкретным студентом.

Архивирование места: показать номер и объяснение «Место исчезнет из активного списка. История сохранится» → причина → «В архив». Для комнаты backend сначала требует архивировать все её места. Архив доступен отдельным фильтром, восстановление явно проверяет вместимость.

## Сотрудники и аудит

OWNER: список сотрудников → «Пригласить управляющего» → логин → получить одноразовый код и срок. Код показывается только один раз, не в URL. Не отправляется автоматически. Изменение роли/отключение: выбранный сотрудник → действие и причина → подтверждение; при необходимости запрос текущего пароля владельца. Для последнего владельца — понятное объяснение запрета.

История — лента «кто · что · когда», подробности показывают только изменённые поля «было → стало» и причину. Архивные объекты открываются из истории. Не использовать JSON и внутренние enum в основном интерфейсе.

## Обязательные состояния

| Состояние | Поведение |
|---|---|
| Загрузка | Skeleton, без временных нулей и случайных старых чисел |
| Пустой список | Понятное объяснение и доступное действие |
| Нет сети | «Нет соединения»; старые данные с временем обновления; записи не отправлять в скрытую очередь |
| Ответ потерян | Сначала повтор с прежним Idempotency-Key, не создавать вторую команду |
| 412 | «Данные изменены другим сотрудником»; перечитать, сохранить ввод для сверки, новый запрос только после проверки |
| 409 вместимость | Обновить доступные места, показать реальное ограничение |
| 401 | Повторный вход; сохранять несекретный черновик формы только в памяти |
| 403 отозван доступ | Убрать защищённые данные, перечитать членства; не показывать кеш как доступный объект |
| 429 | Сообщение о повторе через Retry-After; не перезапускать запрос циклически |
| Ошибка сервера | Нейтральный текст + requestId для поддержки |

Offline-заселение/платежи и локальные автономные изменения не входят в M1. После успешной записи показывать результат сервера; до commit интерфейс не выдаёт успех. Проверки скринридера, клавиатуры, реальных мобильных размеров и critical-flow UI tests обязательны при реализации экранов.
