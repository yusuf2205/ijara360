# M5 — Apps & Accounts (план)

Решения владельца от 7 октября 2026:

| Вопрос | Решение |
|---|---|
| Вход жильца | Одноразовая ссылка-приглашение через @ijara360bot, жилец сам задаёт пароль |
| Доступ из интернета | Открыть всё: анкета, приложение жильца и кабинет сотрудников |
| Платформы | Android (APK) и веб сейчас; Windows после установки Visual Studio; iOS после появления Mac и Apple Developer |
| Уведомления | Лента в приложении + дублирование в Telegram-боте |

Так как кабинет с паспортами становится доступен из интернета, вход сотрудника с нового устройства из интернета подтверждается в Telegram. Из LAN и Tailscale вход работает как сейчас.

## Этапы

Каждый этап: код → backend-тесты → UI-тесты → ревью. Выпуск на production один, в конце, после полного регресса M1–M4.

1. **Права и сессии.** Отдельные права для функций M1–M3: `ROOMS_MANAGE`, `RESIDENTS_MANAGE`, `FINANCE_VIEW`, `FINANCE_MANAGE`, `STAFF_MANAGE`. Миграция выдаёт существующим ADMIN права, равные их сегодняшним возможностям, поэтому поведение M1–M3 не меняется. Устройства и сессии: «запомнить устройство» (30 дней), список устройств, завершение сессии, Bearer-токены для приложения.
2. **Аккаунты жильцов.** `TenantAccount`, приглашение через бота (ссылка 48 часов, одноразовая), задание пароля, вход по телефону и паролю, устройства жильца. Для жильцов без Telegram — ссылка-приглашение, которую сотрудник передаёт сам.
3. **API жильца.** Профиль, комната и место, начисления, оплаты, остаток, аванс, финансовый допуск, только чтение и только своё.
4. **Обращения.** Жалобы, предложения, поломки. Автора видит только SUPER_ADMIN (OWNER), остальные сотрудники получают обезличенные данные на уровне API. Права `TICKETS_VIEW`, `TICKETS_MANAGE`.
5. **Уведомления и лента.** Таблица уведомлений (жильцу и сотруднику), прочитано / не прочитано, доставка в Telegram через очередь с повторными попытками. События: оплата зачтена, начисление создано, ответ на обращение, приглашение.
6. **Realtime-основа (для M6).** Общий канал событий вместо отдельного канала заявок: темы, фильтр по правам и по жильцу, переподключение с повторной загрузкой состояния.
7. **Публичный доступ к кабинету.** Funnel :8443 обслуживает весь сайт; подтверждение входа с нового устройства через Telegram для сотрудников; привязка Telegram в настройках.
8. **Flutter-приложение `apps/mobile`.** Одно приложение: после входа открывается режим жильца или сотрудника. Жилец: главная, оплаты, обращения, уведомления, профиль и устройства. Сотрудник: заявки, жильцы, финансы, обращения — с учётом прав. Мобильный дизайн из прототипа. Сборка Android APK и веб-версии (`/app`).
   Планка качества (решение владельца): подача заявки в приложении должна выглядеть лучше эталонов «Face ID / E-KYC». Это список шагов с отметками и кольцом прогресса, своя камера с рамкой паспорта, подсказками о бликах и размытости и пересъёмкой, овал для фото лица, экран успеха и одна крупная кнопка на экран. Распознавание текста и сверку лица в этом этапе не делаем, только визуальные подсказки.
9. **Проверка и выпуск.** Регресс M1–M4, тесты M5, backup, миграции на копии, deploy, проверка на production, отчёт PASS.

## Не входит в M5

Карты и геолокация (M7), камеры и доступ в здание (M8), AI (M9), гости, push через Firebase, публикация в Google Play и App Store.

## API жильца (этап 3)

Все маршруты требуют сессию жильца: cookie `ijara_tenant` или `Authorization: Bearer`. Сессия сотрудника сюда не подходит, а сессия жильца не открывает маршруты сотрудников. Перед каждым чтением выполняется `finance_refresh_property` под той же блокировкой, что и у сотрудников, поэтому просрочка и допуск всегда актуальны.

| Маршрут | Что возвращает |
|---|---|
| `GET /api/tenant/me` | Имя, телефон, дом, текущая комната и место |
| `GET /api/tenant/finance` | Допуск (`granted`, `reason`), долг, аванс, просрочка (сумма и количество), ближайшее неоплаченное начисление, условия аренды |
| `GET /api/tenant/charges?page=` | Свои начисления по 30, новые сроки сначала |
| `GET /api/tenant/payments?page=` | Свои оплаты по 30, распределение по начислениям, нераспределённый остаток |

Жилец не видит ключи идемпотентности, внутренние комментарии сотрудников, имена сотрудников и данные других жильцов. Записи нет: все маршруты только на чтение.

## Обращения (этап 4)

Типы: жалоба, предложение, поломка. Статусы: новое, в работе, решено, отклонено. Закрытое обращение можно открыть снова.

| Кто | Что видит и может |
|---|---|
| Жилец | Только свои обращения. Ответы подписаны «Администрация», имена сотрудников не показываются. Не больше 10 новых обращений за 15 минут и не больше 20 открытых одновременно |
| `TICKETS_VIEW` | Список и переписка без автора. Комната видна только у поломок, чтобы было понятно, куда идти |
| `TICKETS_MANAGE` | То же, плюс ответы и смена статуса (с проверкой версии). Первый ответ переводит обращение в работу |
| OWNER / SUPER_ADMIN | Всё, включая автора и его комнату |

Обезличивание делает сервер, а не интерфейс. В журнал пишется только факт и тип обращения (`TICKET_CREATED`, `actorId = null`), без автора и текста. Сообщения нельзя менять: у приложения есть права только на `SELECT, INSERT`. Если комнату удаляют, у обращения стирается только ссылка на комнату.

API жильца: `POST/GET /api/tenant/tickets`, `GET /api/tenant/tickets/:id`, `POST /api/tenant/tickets/:id/messages`. API сотрудника: `GET /api/tickets?status=ACTIVE|CLOSED|…&category=`, `GET /api/tickets/:id`, `POST /api/tickets/:id/messages`, `PATCH /api/tickets/:id`.

## Уведомления (этап 5)

Уведомление создаётся в той же транзакции, что и событие. Если действие откатилось, уведомления нет. Копия в Telegram пишется в очередь `notification_deliveries` тоже внутри транзакции, а отправляет её фоновая задача API после commit: проверка каждые 10 секунд, до 20 штук за раз, `FOR UPDATE SKIP LOCKED`.

| Событие | Кому | Telegram |
|---|---|---|
| Новое начисление (`CHARGE_CREATED`) | Жилец | Да, если Telegram привязан |
| Оплата зачтена, с суммой в аванс (`PAYMENT_RECORDED`) | Жилец | Да |
| Ответ на обращение, смена статуса (`TICKET_REPLIED`, `TICKET_STATUS`) | Жилец | Да |
| Новое обращение, сообщение жильца (`TICKET_CREATED`, `TICKET_MESSAGE`) | Сотрудники с `TICKETS_*` и владелец, без автора | После привязки Telegram сотрудником (этап 7) |
| Новая заявка (`APPLICATION_SUBMITTED`) | Сотрудники с `APPLICATION_VIEW` и владелец, без данных заявителя | Этап 7 |

Повторы: 30 с, 2 мин, 10 мин, 1 ч, 6 ч. После 6 попыток `FAILED`. Если Telegram отвечает 403 или 400 (бот заблокирован, чата нет), сразу `FAILED` с причиной `CHAT_UNAVAILABLE`. Строки, зависшие в `SENDING` дольше 5 минут, возвращаются в очередь. В лог попадают только id и номер попытки.

Приглашение в приложение уходит в Telegram отдельно и в ленту не пишется: ссылка в нём секретная, и хранить её в базе нельзя.

API: `GET /api/tenant/notifications?page=`, `POST /api/tenant/notifications/read {ids?}`, `GET /api/notifications?page=`, `POST /api/notifications/read {ids?}`. Каждый видит и отмечает только свои уведомления. В кабинете колокольчик с числом непрочитанных ведёт на страницу `/notifications`, клик по уведомлению открывает связанный раздел.
