# M4 — Applications (заявки на заселение)

Будущий жилец сам заполняет анкету, подтверждает телефон через Telegram и загружает паспорт и фото лица. Администрация рассматривает заявку и заселяет одобренного заявителя через существующий сценарий M2. M1–M3 расширены без переинициализации; M5–M9 не запускаются.

## Сценарий

1. Заявитель открывает `/apply` (или кнопку «Открыть анкету» в боте командой `/start` / `/apply`) и указывает телефон. Создаётся DRAFT и отдельная cookie-сессия заявителя `ijara_applicant` на 30 дней (`httpOnly`, `sameSite=strict`, путь только `/api/public/applications`). Учётная запись сотрудника не создаётся.
2. Телефон подтверждается в Telegram: одноразовая ссылка `t.me/<bot>?start=<token>` живёт 10 минут, бот просит **собственный** контакт (`contact.user_id` = отправитель, личный чат). Номер должен совпасть с номером анкеты. Без подтверждения нельзя загрузить документы и отправить заявку.
3. Анкета: ФИО, дата рождения, ПИНФЛ (14 цифр), паспорт (2 латинские буквы + 7 цифр), учёба/работа, желаемая дата заезда, срок, экстренный контакт, согласие на обработку. Документы: PASSPORT_FRONT, PASSPORT_BACK (от 600×400), FACE (от 480×480); JPG/PNG/WebP, 1 КБ–8 МБ, изображение полностью декодируется при приёме.
4. Отправка (SUBMITTED) проверяет полноту анкеты и документов. Вторая активная заявка на тот же телефон — 409.
5. Рассмотрение: SUBMITTED → UNDER_REVIEW → NEEDS_INFO / APPROVED / REJECTED. NEEDS_INFO и REJECTED требуют комментарий для заявителя; NEEDS_INFO снова открывает анкету для правки. Заявитель может отменить заявку до решения (CANCELLED).
6. Одобрение требует ручных отметок «анкета проверена», «документы проверены», «качество фото лица подтверждено». При совпадениях по телефону/ПИНФЛ/паспорту с другими заявками или с существующим жильцом обязателен письменный результат проверки дублей.
7. Заселение (CONVERTED_TO_RESIDENT) выполняется в той же транзакции, что check-in M2: свободное место, дата, цена, день оплаты, депозит. Если жилец с этим телефоном уже есть, его нужно явно подтвердить (`existingResidentId`); автоматического объединения нет. Архивные комнаты недоступны.

PostgreSQL дублирует инварианты: триггер `guard_application_transition` разрешает только перечисленные переходы и запрещает любой статус кроме DRAFT/CANCELLED без подтверждённого телефона; CHECK `application_conversion` требует resident_id и occupancy_id ровно для CONVERTED_TO_RESIDENT; история статусов неизменяема. Удаление заявок, документов и истории запрещено (RESTRICT, у runtime-роли нет DELETE).

Статусы фиксируются в `application_status_history`, действия — в `audit_logs` (включая каждый просмотр персональных данных, документа и фото лица).

## Защита данных

- Анкета, комментарии для заявителя и результат проверки дублей хранятся только в зашифрованном виде: AES-256-GCM с ключом `KYC_ENCRYPTION_KEY`, контекст записи (id заявки) — AAD, поэтому шифртекст нельзя перенести в другую заявку.
- Для поиска совпадений хранятся HMAC-SHA256 телефона, ПИНФЛ и паспорта, не открытые значения.
- Файлы документов шифруются тем же ключом и лежат вне БД в `KYC_STORAGE_PATH` (`applications/<id>/<kind>/<uuid>.enc`, каталоги 700, файлы 600). Сотруднику изображение отдаётся перекодированным в JPEG (до 1600 px) без EXIF и встроенных метаданных, с `Cache-Control: no-store, private`.
- Загрузка нового файла того же вида не удаляет прежний: старая версия остаётся на диске (неизменяемость и согласованность backup).
- Фото лица отдельно помечено как `biometric_enrollment_sources` с `quality_review` MANUAL_REQUIRED → MANUALLY_ACCEPTED при одобрении. Это источник для будущего M8; распознавания лиц в M4 нет.

**Потеря `KYC_ENCRYPTION_KEY` означает необратимую потерю всех анкет и документов.** Ключ хранится в `secrets/production.env` и должен иметь независимую офлайн-копию (менеджер паролей). Ключ нельзя менять правкой файла: ротация требует отдельной миграции с перешифрованием.

## Права

Роль `SUPER_ADMIN` добавлена; существующий `OWNER` имеет те же полномочия и все права. ADMIN по умолчанию не получает ни одного права M4; владелец выдаёт их в «Настройках» (`PUT /api/permissions/users/:id`), каждое изменение журналируется. Шаблоны («Только просмотр заявок», «Рассмотрение без паспорта», «Полная проверка KYC», «Проверка и заселение», «Без доступа») заполняют отметки, после чего отдельные права можно изменить перед сохранением. Права M1–M3 (комнаты, жильцы, финансы) по-прежнему определяются ролью OWNER/ADMIN и в M4 не менялись.

| Право | Что даёт |
|---|---|
| APPLICATION_VIEW | Список и карточка заявки (ФИО, телефон, учёба/работа, дата заезда) |
| APPLICATION_REVIEW | Начать рассмотрение, запросить данные |
| APPLICATION_APPROVE / APPLICATION_REJECT | Одобрить / отклонить |
| KYC_VIEW_BASIC | Дата рождения, факультет/должность, экстренный контакт, комментарий |
| KYC_VIEW_PASSPORT | ПИНФЛ, серия и номер паспорта |
| KYC_VIEW_DOCUMENTS | Сканы паспорта (вместе с KYC_VIEW_PASSPORT) |
| KYC_VIEW_BIOMETRIC_SOURCE | Фото лица |
| RESIDENT_CREATE_FROM_APPLICATION | Заселить одобренного заявителя |

Одобрение дополнительно требует всех четырёх KYC_VIEW_* прав: нельзя одобрить то, что не видел. Права перепроверяются внутри транзакции под lock property.

## API

Публичные маршруты заявителя (`/api/public/applications`, cookie `ijara_applicant`, та же защита Origin + `X-Ijara-Request` для изменений):

| Маршрут | Назначение |
|---|---|
| GET /config | Включён ли приём, название дома, провайдер подтверждения телефона |
| POST / | Начать заявку `{phone, channel: WEB\|TELEGRAM}` |
| GET /me, PATCH /me | Своя анкета; сохранение черновика с `version` |
| POST /phone | Ссылка подтверждения в Telegram |
| PUT /documents/:kind, GET /documents/:kind | Загрузка (тело — само изображение) и просмотр своего документа |
| POST /submit, POST /cancel | Отправить / отменить с `version` |

Сотрудники (`/api/applications`, сессия сотрудника): `GET /?status=&page=` (по 30), `GET /:id`, `POST /:id/review`, `POST /:id/convert`, `GET /:id/documents/:kind`. Права: `GET /api/permissions/me`, `GET /api/permissions/staff`. Все изменения проверяют `version`; устаревшая версия — 409.

`WS /api/events`: события `application.*` для сотрудников с APPLICATION_VIEW того же дома (только id, без данных); при смене прав — `permissions.changed`. Сессия и права перепроверяются каждые 5 секунд. Интерфейс при обрыве соединения перечитывает данные и переподключается.

Ограничения частоты: начало заявки 10 за 15 минут с IP и 3 на телефон, 5 запросов подтверждения и 30 загрузок на заявку.

## Публичный доступ к анкете

Служебная система по-прежнему доступна только из LAN (`https://192.168.1.105:8446`) и tailnet (`https://mynas.tail4bf75c.ts.net:8446`). Заявителю наружу открыта только анкета:

**https://mynas.tail4bf75c.ts.net:8443/apply** — Tailscale Funnel, HTTPS-сертификат Tailscale.

Цепочка: Funnel :8443 → `127.0.0.1:8448` (только loopback NAS) → Caddy `:8081` → web/api. Caddy на этом listener пропускает только `/apply`, `/_next/static/*` и `/api/public/applications[/*]`; всё остальное, включая `/login`, страницы сотрудников, `/api/auth`, `/api/applications`, `/api/events`, `/api/health` и `/api/telegram/webhook`, отвечает 404. NAS admin, PostgreSQL, Docker и staff API наружу не публикуются. `infra/deploy-release.sh` проверяет эти правила на каждом deployment.

Включение (однократно, после deployment с новым gateway): `docker exec tailscale tailscale funnel --bg --https=8443 http://127.0.0.1:8448`. Отключение: `docker exec tailscale tailscale funnel --https=8443 off` — служебный вход :8446 при этом не меняется.

Реальный адрес клиента: API доверяет только приватным адресам gateway (`trust proxy`), Caddy сохраняет `X-Forwarded-For` только на loopback-listener'ах за Tailscale и перезаписывает его для прямых LAN-клиентов. Поэтому ограничения частоты считаются по настоящему IP заявителя, а не по общему адресу прокси.

## Конфигурация и эксплуатация

| Переменная | Обязательна | Назначение |
|---|---|---|
| KYC_ENCRYPTION_KEY | да | 64 hex-символа, `openssl rand -hex 32`. Без неё compose не запустится |
| KYC_STORAGE_PATH | задана в compose | `/var/lib/ijara360/kyc` ← `${IJARA_ROOT}/data/kyc` |
| TELEGRAM_BOT_TOKEN, TELEGRAM_BOT_USERNAME | для приёма заявок | Без них анкету можно начать, но не подтвердить телефон |
| TELEGRAM_MODE | нет, `polling` | Long polling не требует публичного webhook; позиция хранится в `telegram_cursors` |
| PUBLIC_APP_ORIGIN | нет | Адрес анкеты в кнопке бота, по умолчанию APP_ORIGIN |
| APPLICATION_PROPERTY_ID | нет | Если активных домов несколько; иначе первый созданный |

Секреты записываются только на NAS скриптом `sudo sh scripts/configure-m4-secrets.sh` из опубликованного release: он генерирует KYC-ключ из `/dev/urandom` (если его нет; существующий не меняет), добавляет публичный origin в `ADDITIONAL_APP_ORIGINS`/`PUBLIC_APP_ORIGIN`, запрашивает токен бота скрытым вводом и подтверждает его через Telegram `getMe`. Значения не выводятся и не передаются в аргументах команд; перед изменением сохраняется копия `production.env.before-m4-*`. Deployment (`scripts/Deploy-Nas.ps1`) выполняет release через `sudo`, пароль NAS запрашивается в терминале.

Каталог `data/kyc` создаёт сервис `migrate` (root) с владельцем `node` и режимом 700; API работает без root.

Backup (`scripts/backup-nas.sh`): после `pg_dump` создаётся `ijara360-<stamp>.kyc.tar` с SHA-256 — зашифрованные файлы в том виде, как они лежат на диске. Архив делается после дампа, поэтому покрывает все `storage_key` в дампе. `verify-backup-nas.sh` проверяет обе контрольные суммы, восстанавливает БД и сверяет, что каждый документ из восстановленной `application_documents` есть в архиве. Retention 14 дней для обоих файлов.

Восстановление документов: остановить `api`, затем от root

```sh
tar -C /volume1/docker/ijara360/data/kyc --same-owner -xf /volume1/docker/ijara360/backups/ijara360-<stamp>.kyc.tar
```

и восстановить дамп того же `<stamp>`. Без исходного `KYC_ENCRYPTION_KEY` архив бесполезен.

Тест Telegram подменяет только транспорт (`call`), обработка update проходит по production-коду. `scripts/test-telegram-contact.cjs` предназначен исключительно для тестовой среды NAS.

## Границы поставки

- Проверка паспорта и лица ручная; OCR, сверка с госреестрами и распознавание лиц не выполняются.
- Сроки хранения: `retention_policy=MANUAL_REVIEW`. Автоматическое удаление отклонённых/отменённых заявок и их файлов не реализовано и требует утверждённой политики.
- SMS-подтверждение не реализовано; единственный провайдер — Telegram.
- Off-NAS копия backup (включая `.kyc.tar`) и копия ключа шифрования остаются инфраструктурными задачами владельца.
